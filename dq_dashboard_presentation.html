Part 1 · The Foundation

Data Metric Functions (DMFs)

  • A function that measures one quality dimension on a column/table and returns a number — a health probe for your data.
  • System DMFs — built-in, zero code, cover ~90% of needs.
  • Custom DMFs — SQL functions you write for business rules; behave just like system ones once attached.
  • Attached to the table with one command; runs on a schedule; every result stored over time → a trend, not a snapshot.
Key idea: quality is declared on the object itself, not bolted on from the outside.
Part 1 · Breadth

System DMFs — covered out of the box

Accuracy / Validity

Nulls, blanks, whitespace, casing, negatives, future dates, special chars.
NULL_COUNT · BLANK_COUNT · NEGATIVE_COUNT · FUTURE_TIMESTAMP_COUNT · UNTRIMMED_STRING_COUNT

Uniqueness

Duplicates, distinct counts, allowed value sets.
DUPLICATE_COUNT · UNIQUE_COUNT · ACCEPTED_VALUES

Volume

Sudden growth or drop in a table.
ROW_COUNT

Freshness

Time since the table last changed — catch a stalled pipeline.
FRESHNESS

Statistics

Profile a column, spot distribution drift.
AVG · MIN · MAX · MEDIAN · STDDEV

Schema

Unexpected structural changes.
SCHEMA_CHANGE_COUNT

Most real-world data problems are already covered with zero custom code.
Part 1 · Your Rules

Custom DMFs & scheduling

Custom DMFs = SQL returning a count

  • Referential integrity — orphan orders with no matching customer.
  • Range checks — discount outside 0–50%, amount below zero.
  • Format checks — email not matching x@y.z.

Anything you can express in a query becomes a monitorable metric — and lives in version control.

DATA_METRIC_SCHEDULE

  • TRIGGER_ON_CHANGES — evaluate whenever data changes.
  • Interval / cron (e.g. 5 or 60 min) — required for anomaly detection (needs a regular time series).

Set cadence per table by how critical & fast-moving the data is.

Part 2 · Make it Actionable

Expectations — metric → pass / fail

  • A DMF gives a number. An expectation attaches a rule → VALUE = 0, VALUE <= 3, VALUE >= 10.
  • Each has a readable name → a failure reads like a business statement.
  • Those named failures become the incidents you triage in the dashboard.
status: VALUE = 0 no_duplicate_emails: VALUE = 0 min_volume: VALUE >= 10 no_negative_price: VALUE = 0 valid_status: VALUE = 0
DMF = measurement. Expectation = judgement. Together → a clear, named signal.
Part 3 · The Unknown

Anomaly detection — catch what you didn't think of

How it works

  • Enable ANOMALY_DETECTION = TRUE on ROW_COUNT & FRESHNESS.
  • Snowflake learns the normal pattern → forecast, bounds, is_anomaly flag.
  • Catches: volume spike/drop, freshness staleness.

Automatic Insights

  • Snowflake auto-monitors your "popular" tables (by query activity).
  • Zero DMF setup — volume & freshness watched in the background.
  • Trains on ~2 weeks of activity, then just works.
Expectations = known rules. Anomaly detection = unknown surprises. You need both.
Part 4 · Close the Loop

Notifications — push, don't watch

  • Wire DMF results to email or Slack / webhook at the database level.
  • cooldown_hours — minimum gap between alerts, so no flooding.
  • metadata_included — table, column & DMF name right in the message.
  • Silence a specific noisy DMF while a known issue is being worked.
Monitoring becomes a push system — owners are told the moment a check fails or an anomaly appears, with context to act.

Wrap-up
